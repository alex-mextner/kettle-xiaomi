# Kettle power pulse и Kettle plug keep on

Два блюпринта Home Assistant для чайника Yunmi (`custom_components/yunmi_kettle`) с умной розеткой:

- `kettle_auto_off.yaml` «Kettle power pulse at target temperature»: предсказывает момент достижения целевой
  температуры и коротко обесточивает розетку (импульс). Чайник сам греет до 100 °C, импульс останавливает нагрев.
- `kettle_plug_keep_on.yaml` «Kettle plug keep on»: возвращает питание розетки после обрыва (к температуре отношения
  не имеет).

Удержание температуры (keep warm) **не используется** ни блюпринтом, ни автоматизацией. Нижнюю кнопку чайника
(нагрев до температуры профиля) пользователь нажимает сам, это вне автоматизации: блюпринт реагирует только на
статус `heating`.

## Как работает «Kettle power pulse»

1. Условие: розетка включена, статус чайника `heating`, вода ниже порога. Порог = цель - `offset`.
2. На каждом новом показании температуры считается скорость нагрева (среднее по последним точкам, одно показание
   меняет оценку не больше чем на -30 % / +40 %; точки с интервалом вне 2-90 с или скоростью вне 0.05-1.5 °C/с
   отбрасываются) и время до порога `t = (порог - T) / скорость`.
3. Если `t` не больше `poll_period_seconds` (12 с, то есть порог будет достигнут раньше следующего показания),
   запускается таймер на `t - latency_seconds - возраст показания`. По таймеру розетка выключается и через
   `restore_after_seconds` (2 с) включается обратно. Следующее показание, смена статуса, выключение розетки
   или сброс флага отменяют таймер.
4. Запасной путь: если показание уже на пороге или выше (триггер по фронту «показание >= порог»), импульс делается сразу.
5. Один импульс на нагрев: флаг `input_boolean.kettle_heat_armed` гасится импульсом и любым выключением розетки.
   Снова он включается **только** началом нового цикла: розетка off -> on после настоящей паузы (дольше
   `restore_after_seconds` + 20 с, то есть не собственный возврат после импульса) или смена статуса чайника с не-нагрева
   на `heating` (например `standby` -> `heating`). Температурой флаг не включается и при старте HA не трогается.
   В эти же моменты оценка скорости сбрасывается на `heat_rate_default`. Статус `heating` после импульса, горячие
   показания, провал и новый подъём температуры, обрыв BLE (`unavailable` -> `heating`) второй импульс не вызывают.
6. Failsafe: розетка включена, статус `heating`, вода ниже порога, и так непрерывно `max_heating_minutes` (15)
   минут (таймер сбрасывается, если условие пропадает): розетка выключается и не возвращается,
   `input_boolean.kettle_failsafe_tripped` включается (его уважает «Kettle plug keep on»). Флаг цикла не нужен:
   после импульса статус не `heating`, поэтому failsafe после импульса не срабатывает.
7. unavailable/unknown температуры или статуса не вызывают никаких действий.
8. Уведомления: persistent notification и/или `notify_service`.

### Входы

| Вход | По умолчанию | Смысл |
| --- | --- | --- |
| `water_temperature` | `sensor.kettle_water_temperature` | температура воды |
| `status_sensor` | `sensor.kettle_status` | статус чайника |
| `heating_statuses` | `heating` | статусы, считающиеся нагревом |
| `switch_entity` | обязательный | розетка |
| `target_temperature` | 75 | целевая температура, °C |
| `target_override` | пусто | необязательно: input_number/number вместо `target_temperature` |
| `offset` | 3.5 | выключить на столько градусов раньше цели |
| `restore_after_seconds` | 2 | пауза импульса, 0 = не включать обратно |
| `max_heating_minutes` | 15 | failsafe |
| `latency_seconds` | 1.4 | от решения до выключенной розетки |
| `poll_period_seconds` | 12 | ожидаемый интервал между показаниями |
| `heat_rate_default` / `heat_rate_entity` | 0.39 / `input_number.kettle_heat_rate` | стартовая и текущая скорость, °C/с |
| `armed_entity` | `input_boolean.kettle_heat_armed` | флаг цикла |
| `failsafe_flag_entity` | `input_boolean.kettle_failsafe_tripped` | флаг failsafe |
| `notify_service`, `persistent_notification` | пусто, да | уведомления |

### Откуда числа (живой тест 2026-10-20, одна серия, объём воды неизвестен)

Нагрев 37 -> 78 °C за 104.6 с, 0.392 °C/с (шаги 0.33-0.44). Задержка от показания до розетки off 1.38 с.
Перелёт при импульсе по порогу 75 (показание 78): итоговые 82 °C. Из них 3 °C - показание уже было выше порога,
остальное - задержка и инерция нагревателя, это `offset` 3.5. Реальная пауза импульса на розетке Tuya была 9.3 с
при настройке 2 с (облако Tuya). `latency_seconds`, `heat_rate_default`, `offset` взяты отсюда: при другом объёме
воды скорость пересчитывается по показаниям уже на втором показании, а `offset` придётся подбирать.

## Динамический интервал опроса (патч компонента)

Компонент `yunmi_kettle` только опрашивает чайник; интервал по умолчанию 60 с, одно полное чтение около 6 с
(замер: 5.83 и 5.67 с), раз в 60 с недостаточно для предсказания. Патч
`patches/yunmi_kettle-dynamic-interval.patch` в репозитории (около 20 строк в `coordinator.py`, `const.py`,
`protocol.py`) сам меняет `coordinator.update_interval`:

- статус `heating` (1): опрос каждые 5 с после предыдущего, читаются только статус и температура
  (две подписки, оценка около 1 с вместо 6, не измерено на живом нагреве). Если быстрое чтение упало или
  вернуло не оба значения, делается один повтор полным чтением (без зависания: каждое чтение ограничено своим
  таймаутом; если упало и оно, обычная обработка ошибки: сброс соединения, обычный интервал);
- любой другой статус: интервал из настроек интеграции (`poll_interval`, 60 с), полное чтение;
- ошибка BLE: сразу обычный интервал.

Патч написан для `opravdin/hass-yunmi-kettle-ble` (commit `0b3db91e30c7b1cafe287c7c049c481e233ddef1`, version 0.2.0).
После обновления компонента (HACS или вручную) патч нужно применить заново:
`cd <config> && git apply <repo>/patches/yunmi_kettle-dynamic-interval.patch` (проверено `git apply --check`)
и перезапустить Home Assistant (модуль Python загружается один раз, перезагрузки записи интеграции недостаточно).
Если новая версия изменила `coordinator.py`, `const.py` или `protocol.py`, патч может не лечь: `git apply --check`
скажет это заранее.
Блюпринт при этом ничего не опрашивает сам: цикл `update_entity` из прежних версий удалён. Без патча опрос идёт раз
в 60 с, импульс сработает по запасному пути с большим перелётом.

Первый нагрев замечается не раньше следующего обычного опроса (до 60 с), потом опрос ускоряется. Это
время нагрева до 23 °C: при нагреве от холодной воды до 75 °C не страшно, при подогреве тёплой воды можно получить перелёт.

## Kettle plug keep on

- Розетка вернулась после обрыва (`unavailable` -> `off`): через 4 с `switch.turn_on`, до 3 попыток с паузой 10 с.
- Старт HA: ждёт доступности розетки (до 2 мин), если она выключена и failsafe-флаг не стоит, включает.
- Ручное выключение в HA не отменяется (действует только переход из unavailable и старт HA).
- Пока включён `input_boolean.kettle_failsafe_tripped`, розетка не включается. Флаг сбрасывается включением розетки
  любым способом или выключением самого хелпера.
- Розетка Tuya (Smart Socket 16A, `product_id` 3nprwiontzyzpzng): настройки «состояние при включении питания» в
  диагностике нет (только `switch_1` и `countdown_1`), поэтому «включена по умолчанию» делает эта автоматизация.

## Хелперы

- `input_boolean.kettle_heat_armed`: флаг одного импульса на нагрев;
- `input_boolean.kettle_failsafe_tripped`: failsafe выключил розетку;
- `input_number.kettle_heat_rate` (0..5 °C/с, шаг 0.001): оценка скорости нагрева.

Для второй розетки нужны отдельные хелперы (указать во входах).

## Пример установки

- `automation.kettle_power_pulse` (id `kettle_power_pulse`): блюпринт `kettle_auto_off.yaml`, `switch_entity: switch.<plug_entity_id>`,
  остальные входы по умолчанию.
- `automation.kettle_plug_keep_on` (id `kettle_plug_keep_on`): `kettle_plug_keep_on.yaml`, та же розетка.
- Патч `yunmi_kettle-dynamic-interval` применяется к `<config>/custom_components/yunmi_kettle` (`coordinator.py`,
  `const.py`, `protocol.py`), затем перезапуск HA. Откат: `git apply -R patches/yunmi_kettle-dynamic-interval.patch`
  и перезапуск HA.

Настройки самого чайника блюпринт не трогает. `switch.kettle_keep_warm_after_boil` в компоненте названа неточно:
по спецификации MIoT это `siid 3 / piid 2` `insulation-switch` («lift-memory»: память удержания после подъёма чайника с базы),
а не режим кипячения (он в `siid 3 / piid 1` и в HA не выведен).

## Создать автоматизацию

UI: Settings -> Automations & scenes -> Blueprints -> «Kettle power pulse at target temperature» -> Create automation,
выбрать розетку, остальное по умолчанию. YAML (`automations.yaml`):

```yaml
- alias: Kettle power pulse
  use_blueprint:
    path: kettle/kettle_auto_off.yaml
    input:
      switch_entity: switch.<plug_entity_id>
      # необязательно: target_temperature: 75, offset: 3.5, restore_after_seconds: 2,
      # max_heating_minutes: 15, target_override: input_number.kettle_target, notify_service: notify.mobile_app_<phone>
- alias: Kettle plug keep on
  use_blueprint:
    path: kettle/kettle_plug_keep_on.yaml
    input:
      switch_entity: switch.<plug_entity_id>
```

## Что не проверено

- Полный цикл на настоящем чайнике с предсказанием и новым `offset`: проверено только на фейковых сущностях.
- Динамический интервал на живом чайнике: логика проверена на настоящем `DataUpdateCoordinator` с подменой BLE
  (интервал 90 из options -> 5 при статусе 1 -> 90, подмножество свойств в быстром режиме, сброс при ошибке BLE).
  После перезапуска HA с патчем чайник был вне зоны (розетка выключена пользователем), живой опрос с патчем не
  проверен: ни в standby, ни на нагреве.
- Время быстрого чтения (две подписки), реальный период около 6 с, и работа предсказания при нём.
- Откат на полное чтение при неполном/ошибочном быстром чтении проверен только на заглушке BLE.
- Поведение розетки Tuya при настоящем обрыве питания.
